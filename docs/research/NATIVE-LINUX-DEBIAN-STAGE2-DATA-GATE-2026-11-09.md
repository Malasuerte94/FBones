## Source findings that determine assertions

before showing the dirty-project dialog. A valid pending bone-name draft may
therefore become an authored dirty rename before Cancel. Assert its exact value
survives, the old live session remains dirty/usable, and the previously saved
file is unchanged. Do not assert preserved focus, an uncommitted draft or the
pre-flush revision. `cancelDiscard` resolves update preparation false; the
controller sends the native install request only after preparation succeeds.

After ordinary Save, native `with_update_guard` checks the exact clean revision
under the Session mutex before plugin installation. The updater verifies the
package signature and authenticated version again during installation. Ready
already means the stock download/signature path completed; a separately hashed
package is supporting identity, not a replacement for that app observation.

Actual locked Tauri2.12.5 `AppHandle::restart` ultimately calls
`process::restart`: Linux spawns `current_binary` with the retained arguments,
then the old process exits0. It does not exec into the same PID. Spawn failure
also reaches old exit0, so an old terminal alone cannot prove restart. Require
a distinct automatic successor PID/start and its actual new image. The own
subreaper capability supplies a way to obtain the real successor terminal;
actual application adoption and unchanged control-provider behavior still need
observation in this new case.

The stock updater2.14.1 Debian path invokes ordinary pkexec, then graphical
sudo, then terminal sudo. Initial harness `sudo dpkg` installation does not prove
the updater route. Do not add an auth shim, alter policy/security, capture a
password or replace the plugin's process. If a real authorization prompt cannot
be handled through the existing standard environment without credentials, retain
the precise provider block and stop. AppImage is a separate future case.

### Declared adoption variant before implementation

The automatic spawn→old-exit interval has no toy handshake and may be shorter
than a `/proc` poll. A live immediate-old-parent observation is therefore not a
mandatory acceptance condition. A fresh retained wrapper may set its own
subreaper flag, prove it, and create **only the old FBones main process**. Start
watching the closed own descendant tree before Install. If the successor is
first observed already adopted, require a new PID and exact kernel start,
actual PPID equal to that same retained wrapper, live waitable-child provenance,
the previously extracted member SHA, own native window and visible0.9.6. Require
the old main's actual exit0 and the successor's eventual exact waitpid normal0.
The wrapper/source/creation ledger must exclude a second FBones launch before
automatic verification and normal close; no POST session or recovery launch is
allowed in that interval. Ambiguous candidates fail rather than choosing one.

Linux's documented subreaper guarantee and the measured own capability establish
that this adopted child descends from the closed own process tree. Label the
result **descendant adoption proven; immediate creator not observed** when the
brief direct-old-parent phase was missed. Do not claim a live toy-style handshake
or exact parent interval that was never captured. Record auxiliary descendants
separately; do not input, signal or reap unrelated/insufficiently bound children.
Do not instrument or suspend the product to lengthen the observation window.
This explicit provenance variant reuses the [documented and measured provider](NATIVE-LINUX-SUBREAPER-DATA-GATE-2026-11-09.md);
it does not relax successor image/version/start or real terminal requirements.

second app, unchanged file bytes, and its own retained normal exit0. This proves

upgrade. If Open cannot be completed, report actual-upgrade acceptance only to
the observed stage and keep file-persistence acceptance open.

# Windows core90: observe natural dialog/installer foreground changes

Pre-code refinement to the [core90 Windows scenario](NATIVE-WINDOWS-CORE90-UPGRADE-UI-ADDENDUM-2026-11-11.md). The accepted Updates-only pointer case requires foreground unchanged because that action merely closes a renderer panel. The shipped Open action creates a PowerShell-STA native OpenFileDialog, and clean Install may create a stock NSIS installer. Those intended OS windows can naturally receive foreground after the same scoped child-message click, even though the controller never activates a window.

In the fresh core scenario only, retain raw before/after foreground HWND/PID for old-open, fresh-open and clean-install as an **unresolved observed transition**. Do not label any change safe solely because it followed a click. Acceptance requires the subsequent exact newly created PowerShell-child/dialog or inherited owned-Job installer association, with fresh start/executable/parent or Job membership and current native-window identity. An unknown/broker-escaped/unassociated window stops the case. If foreground is unchanged, the same actual dialog/install postcondition is still required.

This is no activation permission: add no SetForegroundWindow, BringToTop, focus, SendInput, global mouse/keyboard or arbitrary recovery. Preserve physical geometry/hit-test/root/created-provider ownership, one durable intent and one message sequence per intended action. Updates retains the original unchanged-foreground requirement. This source-backed action-specific observation policy avoids rejecting legitimate intended native windows while preserving strict failure on unknown ownership; actual Open/Install effects remain to be measured. No target/provider/CI operation by this reviewer.

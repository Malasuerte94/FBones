## Why this bounded query

The prior own toy's main succeeded but its requested agent produced no record.
A separate static lead matched the bundled standard JVM's isJVMTIIncluded
native registration and normal false-return tail to a pinned public OpenJDK
implementation. That is a source-backed inference, not vendor build provenance
or runtime capability proof. The independent private static-lead-check.json
verifies the referenced PE bytes; no function was called there.

Before execution the new C/PE review verified a single own-class classpath,
explicit pinned JVM, only JNI initialization and three versioned GetEnv requests.
Non-null pointers are used only on JNI_OK. Success branches read version, phase,
potential/granted capabilities and dispose their own environment. No AddCaps,
callbacks, agent DLL/options, attach or editor classes exist in this probe.

[Oracle's JVMTI environment specification](https://docs.oracle.com/en/java/javase/17/docs/specs/jvmti.html#environments)
documents GetEnv-created environments and JNI_EVERSION for incompatible or
unsupported interfaces/current configurations. It permits compatible returned
versions to differ from the requested one. Its
[capability documentation](https://docs.oracle.com/en/java/javase/17/docs/specs/jvmti.html#GetPotentialCapabilities)
separates live-phase potential capabilities from the OnLoad set. These primary
Java17 documents guide interpretation; they are not exact bundled-build proof.

## Limits and stopping point

This direct result is consistent with the static exclusion lead. It does not
recover exact vendor build flags or every cause of the prior missing agent
output. It does not prove all Windows/JVM observation impossible, original
launcher forwarding semantics, editor method identities, Physics caller clocks
or exported numerical phase. No solver/model failed in this probe and none was
changed. Stop before repeating the failed agent route or querying an original
process. Any different future observation route needs its own justified gate.

## Collection and preservation gates

Root first opens/saves the new own fixture and obtains a clean, stable canonical
baseline. DATA independently verifies it, retaining original bytes and any
unmodeled editor metadata. Then root creates **two fresh own forks of those same
baseline bytes**, one Offset header Match and one Properties header Match.
Target selection must prove the second constraint's exact name. Do not chain
buttons, type values, toggle mixes or sample another target.

Both first actions should author a change under every frozen candidate; this is
not proof of original history/no-op behavior. **Do not repeat either click**:
with nonzero mix, the first edit can change the next sampled pose, so accepted
zero-mix repeat no-ops do not generalize.

Offset may change only its six offsets; properties and all24 cells remain exact.
Properties may change only its ordered runtime endpoint fields/cache; global
offsets/mixes stay exact. Both preserve all authored bone bits, driver fields,
source, ordered targets, flags and route inventory/order. No evaluated pose is
baked into bones. Failed input or unproven button selection is an adapter limit,
not a sampling observation. Any future product change requires the paired
actual result, not this hypothesis table.

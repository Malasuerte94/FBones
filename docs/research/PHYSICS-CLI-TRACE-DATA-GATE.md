## Why exactly one new discovery probe is justified

A supported diagnostic flag is a distinct possible observation route. A small
new original invocation can answer whether it actually exposes a useful caller
datum; another numeric model or a600-frame rerender cannot answer that. This
is a **log-content feasibility probe**, not a parity experiment, recovered
schedule, confirmed logging contract or authorization to implement a solver.

Before any execution the coordinator and paired reviewers must freeze a NEW
own recipe/settings and resource-isolation gate. Proposed bounded profile:

- One short uniquely named animation, one carrier step and two X-only Physics
  constraints. An inert90Hz control and60Hz restoring constraint exercise the
  already observed highest-rate coupling without reusing an accepted render.
- New own source/animation/bone/constraint names, tiny own opaque assets, fps60,
  warmUp0 and no title/bone overlays. Use roughly three output intervals and
  predeclare a hard budget of **at most4 PNGs**; do not guess exact endpoint
  inclusion from f32 duration or repair an unexpected count after collection.
- One isolated original process, exact `--update 4.3.26` plus `--trace`, at most
  one own import and one tiny animation export in that invocation. Reuse the
  proven multi-operation command path and mapped drive. Do not recollect JSON/
  pixel oracles or the old60/90 batches. No second untraced numeric control is
  required to discover log content, and this probe cannot claim equivalence
  to normal untraced dynamics.
- Exclusive fresh output files and complete stdout/stderr/terminal/identity/
  source/settings hashes. Require the current original-resource owner to be
  finished and the immediate actual original-instance preflight to pass. Never
  forward into an existing user/own GUI or rely on an undocumented isolation
  switch. Root remains the only original operator; no collector is written here.

The short source is intentionally a new content probe, not a modified version
of the five-animation causal experiment. It supplies no inference about the
old animation traversal/reset history or old residual curves.

## Predeclared useful datum and stop rules

First establish flag recognition, exact editor4.3.26, the intended own source
and successful operation. A successful exit alone does not prove trace effect.
Do not add `--ignore-unknown`, alter launcher settings, activation, logging
internals or try alternative hidden flags after an unsupported-option result.

To advance the caller investigation, a log must explicitly identify at least
one **executed physics/replay boundary**—for example an update mode and its
simulation time or an actual ordered replay-step count—bound to the own
animation/export context. Preserve the raw line and distinguish wall-clock
logging timestamps, authored FPS/settings echoes and final output labels from
actual simulation timing. A partial datum is not a complete caller schedule;
mode/time units and stage interpretation need their own evidence.

If logs contain only startup, settings, checks or export progress, record
`NO_CALLER_DATUM_FOUND_FOR_THIS_TRACE_PROBE` and stop this route. This means no
useful datum for the bounded operation, not that no diagnostic feature could
ever log anything. A diagnostic assertion/error or unexpected source/count
also stops with the actual failure; do not treat absence as an empty update.

Even a useful trace describes the **traced diagnostic execution**. Do not
silently promote it to the normal exporter's behavior, fit a clock/epsilon/
lag grid, rerun rejected operators, or change production. The next action would
be independent DATA/UI review of that one actual datum and an explicitly
approved narrower caller contract, reusing existing measurements if appropriate.

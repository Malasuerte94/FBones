# Native v5: observed control providers versus ARIA proxies

Pre-code UI finding from retained hosted run4. Windows completes the stock
installation/full owned-window predicate and normal cleanup0. CIM returns six
owned WebView2 descendants mentioning the private profile, but no debugging
port flag and zero listeners. This is not ambiguous IP duality and gives no
CDP control capability. Stop that transport; do not change browser policy,
devtools settings, product CSP or the stock executable to enable it.

One new bounded provider question is justified: does the exact retained native
main window expose visible version0.9.5 and a unique enabled **Updates** button
through Windows UI Automation, with an actual InvokePattern and one scoped
panel/current-version transition? Inventory the owned window before input,
bind PID/start/image/HWND and native element ownership, and stop on an absent/
ambiguous provider/control. No desktop-wide/global input or browser replacement.
Version, updater support, one action and normal-close acceptance stay required.

The unchanged UpdateNotice button contains a stable **Updates** span plus
optional download-percent/byte text or a ready dot's accessible0.9.6 label.
Exact whole-button Name/AXTitle `Updates` is therefore not a proven invariant.
Prefer a unique owned Button associated with its exact **Updates** text child,
retaining runtime/object identity while recording the composite name. Otherwise
use a closed full-label grammar: Updates alone, a source-valid integer0..100%
suffix, or the exact0.9.6 ready label, with normalized whitespace. Unknown-size
byte progress is another source-valid form; do not call it a product error if
the bounded probe declines that label. Never accept an arbitrary prefix/first
match. Recheck the same enabled owned element and qualified label/associated
child before one action; status-text changes alone need not change its identity.

macOS now directly passes the SDK own-provider prerequisite, stock kernel/start/
image and visible window, Aqua/AX and normal close0. Captured own stdout says
`FBones UI ready; renderer=webgl`. It fails the combined unmeasured AXWebArea/
Viewport-label assertion, without a retained accessibility inventory. That
source-selected ARIA-to-AX proxy was never measured as a native renderer-ready
contract; its absence does not overturn the actual renderer signal, and the
signal alone does not prove working Updates controls.

Retain one bounded own AX inventory. A fresh capability scenario may distinguish
actual stock renderer-ready signal plus owned visible native window from AX
role/Viewport-label observations. Require visible0.9.5, no startup error, unique
enabled **Updates**, one permitted scoped action and actual current-version/
panel transition, plus strong SDK identity and normal close0. Record the AX
role/label outcome separately as measured/unknown; no pixel, accessibility
parity, full frontend, installed-upgrade or permission-bypass claim follows.
This explicitly replaces an unproved proxy with independent renderer and
functional-control evidence, not a silent success after dropping an assertion.
